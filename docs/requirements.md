## 1. 目的

Google スプレッドシートで行っているポーカー会の結果入力、順位計算、チップ総量検算、会費精算を、スマートフォンから使いやすい Web アプリへ置き換える。

当初の MVP は、1つのグループで実際のポーカー会を最初から最後まで運用できる状態を目標とした。現在は同じRiverCheck内で複数グループを作成・切替でき、同一プレイヤーを複数グループへ所属させられる。

今後は次へ拡張する。

- 個人ダッシュボード
- グループダッシュボード
- グループごとに独立した主催者・権限管理
- 他ユーザーによるグループ作成・利用

将来拡張を妨げないデータ設計とするが、不要な機能や抽象化は先行実装しない。

## 2. 利用者

### 主催者

- 開催を作成する
- 開催を参加受付可能な状態にする
- 参加者用リンクを共有する
- 参加状況と入力状況を確認する
- チップ総量の差分を確認する
- 結果を確定する

### 参加者

- 主催者から共有された参加者用リンクを開く
- 登録済みプレイヤーから自分を選ぶ、または新しい名前で参加する
- 自分の残チップとリバイ回数を入力・修正する
- 確定後の結果と精算額を確認する

MVPではログイン機能やユーザーアカウントを設けない。

## 3. 正式な利用フロー

### 3.1 主催者が開催を作る

1. グループTOPから新規開催画面を開く
2. 開催条件と想定参加人数を入力する
3. 想定参加人数に応じた順位別の会費負担額を確認しながら条件を調整する
4. games に open 状態で保存する
5. 開催の主催者画面へ移動する
6. 参加者用リンクを LINE 等で共有する
7. finalized にするまでは、参加人数の変動に応じて開催条件と金額を変更できる

### 3.2 参加者が自分で参加する

1. 参加者は共有された開催URLを開く
2. 本人端末としてプロフィール認証済みの場合は「自分として参加」を押す。未認証の場合は登録済みプレイヤー一覧の自分の行にある「参加」を押す、または新しい名前を入力して「この名前で参加」を押す
   - 未認証で登録済みプレイヤーを選択した場合は「{表示名}として参加しますか？」の確認ダイアログを表示し、「参加」を押すまで参加登録とプロフィール認証を行わない。「キャンセル」では状態を変更しない
3. サーバーはランダムな participant token を発行する
4. participant token の平文は参加者のブラウザだけに保持する
5. DBには participant token のハッシュだけを保存する
6. 同じ開催・同じ group_player が既に別tokenで使用中なら参加を拒否する
7. 同じブラウザに正しいtokenが残っている場合は、その参加者として再開できる
8. open 中は途中参加を受け付ける
9. ドタキャン時は主催者が参加者を開催から外せる

参加者用URLを開くGET、loaderの再実行、フォーカス・pageshow・再検証では参加登録しない。プロフィール認証済みの場合も、本人が参加ボタンをPOSTするまでgame_participantsを作成しない。

「招待」とは、主催者が参加者を事前にチェック選択することではなく、参加者用リンクを共有して各参加者が自分で参加することを指す。

登録済みプレイヤー一覧は、確定済み開催への参加回数が多い順、同数なら最終参加開催日が新しい順、その後は表示名順とする。常連を自動的に上へ表示し、MVPでは手動のお気に入り・並び順管理を設けない。

### 3.3 リバイを記録して結果を入力する

1. 参加者本人はゲーム中に「＋ リバイ」と「100BB返済」だけを1操作で記録できる
2. リバイは累計と未返済を1ずつ増やし、返済は未返済だけを1減らす
3. 現在スタックはアプリへ入力せず、150BB超では任意返済、300BB超では必須返済として本人が判断して記録する。返済後も300BBを超え、かつ未返済が残る場合は繰り返す
4. 返済条件と開催ごとの72oボーナス・ボムポット設定は、受付中の参加者画面にある「ローカルルールを確認」から同じボトムシートで確認でき、確定結果画面には表示しない
5. 主催者は参加者一覧から同じ操作を代理入力でき、累計・未返済・終了時リバイ証を救済修正できる
6. 参加者は終了時に自分の remaining_chips と settlement_rebuy_count（手元のリバイ証）を入力する。未入力時のリバイ証は現在の未返済口数で初期化し、利用者が修正した値を優先する
7. outstanding_rebuy_countとsettlement_rebuy_countの一致・不一致を画面に表示する
8. 結果を一度保存した後も、主催者が finalize するまでは同じブラウザからリバイ・返済の記録と終了時入力を修正できる
9. 参加者画面では「プレイ中」のリバイ・返済操作と「プレイ終了後」の結果入力を別セクションで表示する。終了時入力が未保存の場合は入力欄を最初から表示し、保存後は入力値をコンパクトに表示して、確定までは「修正する」から再編集できる
10. open開催へ参加済みの画面では「参加者 {人数}」からページ遷移なしのモーダルを開き、現在参加中の表示名と設定済みの「今日のひとこと」を参加順に確認できる。ひとこと未設定者には空欄用ラベルやプレースホルダーを表示しない。本人行は色・装飾で識別し、表示上の「あなた」ラベルは付けない。リバイ・チップ・結果・精算情報は含めない
11. 参加者本人はopen中だけ、自分の参加者行から開催単位の「今日のひとこと」を24文字以内・1行で設定、変更、解除できる。プリセット候補と自由入力を用意し、空欄保存は未設定として扱う。ひとことはgame_participantsへ保存して次回開催へ引き継がず、変更履歴をGAME TIMELINEへ追加しない。参加者一覧を開くたび既存loaderを再検証して最新値へ同期し、常時ポーリングやWebSocketは導入しない
12. 参加取り消しは確認ダイアログを経由し、誤タップ1回では実行しない
13. finalized 後は参加者が編集できず、参加者一覧の入口も表示しない
14. リバイ・返済の成功後はリバイ操作欄内に直前の成功操作と「元に戻す」を表示する。時間経過では消さず、次の成功操作で置き換え、UNDO成功またはページ再読込・遷移で消える。失敗した操作では直前のUNDO対象を失わない

### 3.4 主催者が結果を確定する

1. 参加者の入力状況を確認する
2. expected_total、reported_total、difference を確認する
3. difference が0でない場合は警告を表示する
4. 記録上の未返済と終了時リバイ証が異なる場合は参加者ごとの差を表示する
5. settlement_rebuy_countがtotal_rebuy_countを超える場合は修正するまでfinalizeできない
6. 警告を確認したうえで、チップ差分・リバイ記録差があっても主催者判断で finalize できる
7. finalize処理で点数、順位、会費負担を計算する
8. 確定値を game_results に保存する
9. gameを finalized にする
10. 主催者画面で確定前に編集した会費・想定人数・順位別負担額は、開催ごと・端末ごとの精算プレビュー下書きとしてブラウザのlocalStorageへ自動保存し、同じ端末で管理画面を開き直したときに復元する。下書きは正式なgame設定や実績・ランキングへ影響しない
11. 精算プレビューには下書き保存済み表示と「元の設定に戻す」を用意し、正式設定へ戻した場合、結果確定成功時、または受付中開催の削除成功時にその開催の下書きを削除する。別端末には同期しない

### 3.5 グループTOPで開催を探す

開催一覧は状態を混在させず、未確定の開催を上段「受付中」、finalizedの開催を下段「過去の開催」に分ける。各区分内は開催日の新しい順とする。

- 受付中カードは状態と開催日を表示し、一般参加者は「参加ページ」、主催者ログイン中は「開催管理」へ進む
- 受付中が0件の場合、主催者ログイン中だけ「新しい会を作成」ボタンを表示する
- 過去カードは開催日、確定結果の参加人数、現在の1位プレイヤーを表示し、「結果を見る」へ進む
- 過去カードの人数と優勝者は現在有効な`game_results`から取得し、訂正履歴を集計しない
- 確定結果の見出し内にも開催日を表示し、参加者画面と主催者画面で共通化する

### 3.6 グループを作成・切り替える

- RiverCheckのプレイヤー本人を表す`players`はグループをまたいで共通とし、`group_players`を各グループへの所属として扱う
- 同一playerは複数groupへ所属できるが、同じgroupへ重複所属させない
- 表示名、プロフィール文、アイコン、MY HANDはplayer単位で共通とし、別グループでも同じプロフィールを使用する
- 開催、結果、ランキング、参加回数、獲得実績、装備中実績はgroupまたはgroup_player単位で分離する
- プロフィール認証済みplayerは、所属済みの別グループへ切り替えても同じ本人セッションを利用できる
- 日常操作としてプレイヤーのログアウト導線は表示しない。本人選択を間違えた場合は自分のプロフィール最下部にある「この端末のプレイヤーを変更」から同一グループの別プレイヤーへ切り替え、変更先を確定するまでは現在の本人セッションを維持する
- プロフィール認証済みplayerが未所属グループのopen開催共有URLを開いた場合は、現在のplayerを新しいgroup_playerとして追加し、その開催への参加まで1操作で完了できる。新しいplayers行は作成しない
- `/` は公開グループへ固定遷移せず、本人が利用可能なグループを解決する入口とする。前回グループが現在も利用可能なら自動遷移し、1グループだけならそこへ自動遷移、複数候補を解決できない場合はグループ選択を表示する
- 本人が利用可能なグループを解決できない場合は `river-check` へフォールバックせず、主催者から届いた受付中の開催URLから参加するよう案内する
- 未所属ゲストへ公開する入口はopen開催の参加ページ、主催者ログイン、プロフィールclaim、参加画面で必要なアバター配信に限定する。グループTOP、ランキング、About、管理画面などはグループ所属者または主催者だけが閲覧できる
- 同じ開催URLはgame statusで役割を分ける。open時は未所属者の招待入口として本人選択・新規参加を許可し、finalized時はURL自体を結果閲覧キーとして未所属ゲストにも確定結果だけを読み取り専用で公開する。draftはグループ所属者・主催者・その開催の既存participant tokenを持つ参加者だけが閲覧できる
- finalized開催を未所属ゲストが開いた場合は、グループTOP・ランキング・他プレイヤー戦績・過去開催ナビ・PayPay・TABLE STORIESへの横移動や追加情報を表示しない。本人認証済みメンバーは従来どおりグループ内を閲覧できる
- 一般の「プレイヤーを選択」導線はハンバーガーメニューに置かず、本人選択と新規プロフィール作成はopen開催の招待URLから行う
- この招待導線では無効化済みの既存group_playerを本人操作で再有効化せず、主催者による確認を必要とする
- 主催者はグループ切替画面から新しいグループを作成できる。作成時に主催者端末がplayerとしても認証済みなら、そのplayerを新グループへ自動所属させる
- メンバー管理では、他グループに既に存在するplayerを新規作成せず、新グループへ所属追加できる
- 現在のグループ名は各グループ画面の共通ヘッダー、グループ切替一覧、開催リンクからのグループ招待画面へ表示する
- 一般プレイヤーのハンバーガーメニューでは、有効な所属グループが2件以上の場合だけ「グループを切り替える」をプロフィールの直下へ表示する。1グループだけのプレイヤーには表示しない。主催者は新規グループ作成の入口を失わないよう、1グループ時も同位置に「グループを管理」を表示する
- 主催者はグループ設定からグループ名を変更できる。名称変更では`groups.name`だけを更新し、共有済みURLを壊さないため`public_code`は変更しない
- LINEオープンチャットの招待URLはグループ単位の任意設定とする。URLが設定されているグループだけ「このアプリについて」に参加導線を表示し、空欄で保存したグループには表示しない。既存の`river-check`だけは移行時に現在の招待URLを引き継ぎ、新規グループは未設定で開始する
- 最後に正常表示したgroupCodeを端末localStorageへ保持し、アプリルート`/`からの次回起動時はそのグループへ復帰する。未記録・不正値・localStorage利用不可時は既定グループ`river-check`へ戻す
- 主催者認証はRiverCheck全体で共通のPIN・主催者セッションを使用し、グループごとの独立権限は将来拡張とする

## 4. URL

### 参加者用

```text
/g/:groupCode/games/:gameId
```

このURLは参加、本人確認、結果入力、確定後結果表示の入口とする。主催者画面では「共有リンク」として表示し、入力欄右側のコピーアイコンからクリップボードへコピーできる。

共有リンクの直下からQRコードを開閉でき、読み取ると参加者画面を直接開く。QRには現在の管理画面と同じoriginを使用する。公開HTTPSまたはLAN IPで開いていれば別端末から利用できる。localhostまたは127.0.0.1は別端末から到達できないため、QR表示内でLAN IPから開き直すよう案内する。

### グループ切替

```text
/g/:groupCode/groups
```

本人プロフィールで認証済みの場合は所属中グループ、主催者認証済みの場合は全グループを一覧表示する。主催者は同画面から新しいグループを作成できる。

### 主催者用

主催者ホームはグループ単位の専用URLとする。

```text
/g/:groupCode/manage
```

主催者ホームの上部には「メンバー管理」と「グループ設定」を並べ、開催作成は開催管理の操作として表示する。グループ設定は次のURLとする。

```text
/g/:groupCode/settings
```

グループ設定では開催をまたいで共通利用する設定を扱う。現在はグループ名の変更、LINEオープンチャット招待URL、PayPay受取リンクの登録・更新をここで行い、今後の共通設定も開催ごとの管理画面へ混在させず、この画面へ集約する。

各開催の管理画面は次のURLとする。

```text
/g/:groupCode/games/:gameId/admin
```

主催者画面は開催の作成、開始、開催名変更、受付中開催の削除、条件変更、参加状況確認、参加取り消し、検算、finalizeを担当する。

同じ端末で参加済みの場合、主催者画面に現在の参加者名を表示し、その人の入力画面へ戻る導線を設ける。主催者画面と参加者画面の往復ではフルページ読込を行い、開催ごとの本人Cookieを必ず再判定する。

参加者向けグループTOPと各参加者画面には、迷子防止のため主催者画面への導線を表示する。主催者画面、会作成、メンバー管理、グループ設定、開催管理の全loader/actionは主催者認証を必須とし、未認証時はPIN・合言葉入力画面へ移動する。

認証成功時はPIN自体ではなく有効期限付きの署名済みセッションをHttpOnly、SameSite=LaxのCookieへ180日保存し、本番HTTPSではSecureも付与する。Cookie改ざん、期限切れ、Cloudflare Secret未設定の場合は管理操作を許可しない。PINとCookie署名鍵はCloudflare Secretで管理し、Git、HTML、URL、DBへ保存しない。

## 5. 開催

開催作成時に次を設定する。

- title
- played_at（日付のみ。新規作成時は今日）
- initial_chips（1以上。画面表記は「初期チップ（100BB）」、新規作成時は20,000）
- venue_cost
- first_place_cost
- second_place_cost
- third_place_cost
- cost_shares（全順位。移行前データではNULLを許可）
- seven_deuce_rule_enabled（72oボーナスを適用するか）
- bomb_pot_rule_enabled（ボムポットを適用するか）

`rebuy_chips` は利用者が個別設定せず、常に `initial_chips` と同じ値を保存する。新規作成時の会費は11,330円、想定人数は8人、上位3位の負担額は0円・500円・1,000円とし、4位以下はその3額から自動配分して初期表示する。open中は全順位を自由に調整できる。72oボーナスとボムポットは新規作成時にONとし、open中は開催管理から変更できる。導入前の既存開催は、過去へルールを遡及させないため移行時にOFFとする。

games.status は最低限次を持つ。

- open: 参加受付・入力可能。条件変更と参加者増減が可能
- finalized: 結果確定済み。参加者による入力と開催条件の編集は不可。主催者による確定結果訂正だけを許可

開催作成時点で open とし、基本状態遷移は open → finalized とする。逆方向へ戻さない。

### 開催条件の変更

- 管理画面ではopen中の開催名だけを変更できる。開催日とチップ設定は再編集せず、会費の精算設定だけを表示する
- 開催名を変更しても開催IDと参加者用URLは維持し、新規開催通知は再送しない
- open の間は、会費、想定人数、全順位の負担額を変更できる
- 精算の丸め単位は100円固定で、画面には入力欄を設けない
- finalized 後は変更できない
- 72oボーナス設定はopen中だけ独立して保存でき、finalized後はその開催の設定を固定する
- open 中に条件を変更しても、参加者の入力済み remaining_chips と settlement_rebuy_count は保持する
- finalize 時点の最新設定を点数・検算・精算へ使用する
- 会費精算の人数と実際の参加人数が一致しない場合はfinalizeできず、確定ボタン付近に理由を表示する
- 精算設定の独立した保存操作は設けず、finalize成功時に精算設定と確定結果を同一トランザクションで保存する
- finalize失敗時は精算設定も保存せず、入力値とエラーを画面に残す
- finalize失敗時のエラーは確定ボタンの直前に表示する

### 受付中開催の削除

- 主催者はopen中の開催だけを開催管理画面から削除できる
- 削除前に開催名、参加人数、関連する入力も消えることを確認ダイアログで明示する
- 削除時はgame participantと、それに従属するチップ入力、リバイ履歴を同時に削除し、参加者用URLは以後404とする
- finalizedの開催は削除できず、確定結果、TABLE STORIES、実績の履歴を保持する

### 順位別負担額プレビュー

新規開催作成画面と開催条件編集画面に、想定参加人数を入力するプレビューを設ける。

- 想定参加人数を変更すると、1位から最下位までの負担額を即時表示する
- 全順位を順位ごとの金額パネルで確認でき、金額タップ時だけ入力状態へ切り替えて直接編集できる
- settlement_total と全順位の cost_share 合計も表示する
- 不足額、超過額、合計一致をリアルタイム表示する
- 100円単位でない順位、順位傾斜の逆転、合計不一致は理由を表示し、開催を作成できない
- 「上位3位から配分」では1〜3位の変更を基準に4位以下を既存ロジックで自動再配分する
- 4位以下を編集すると「全順位を個別調整」へ切り替わる
- 「全順位を個別調整」では変更した順位以外へ差額を自動再配分しない
- プレビューは保存対象の参加者ではなく、金額確認用の仮人数とする
- 新規作成時に設定した想定人数を開催条件として保存し、参加人数の増減では自動変更しない
- open 中は想定人数を手動変更して別人数の金額も試算できる
- 会費・想定人数変更時は現在選択中のおすすめモードから全順位を再生成し、古い手動調整は引き継がない
- finalize は保存された全順位配分を使用する。移行前データだけは保存済み1〜3位から従来式で算出する
- おすすめボタンは激しい順に「表彰台ボーナス」「標準傾斜」「ゆる傾斜」「シンプル割り勘」を2列で並べ、全順位のおすすめ額を即時反映する。標準・ゆる傾斜は「上位3位から配分」へ戻し、表彰台ボーナス・シンプル割り勘は「全順位を個別調整」へ切り替える
- 表彰台ボーナスは6人以上だけで利用でき、1位を無料、2・3位を優遇し、4位以下をなだらかに傾斜させる
- おすすめ反映時は `max(想定人数, 現在の参加人数, 4)` で計算し、現在の参加人数が想定を超えていれば想定人数も更新する

## 6. プレイヤーと参加者

### players

人そのものを表す。display_name を持ち、同名を許可する。識別にはUUIDを使う。

### group_players

プレイヤーのグループ所属を表す。同じ player が将来複数の group に所属できる。

### game_participants

受付中の参加状態と現在入力値を表す。

- game_id
- group_player_id
- participant_token_hash
- status
- status_text（開催単位の「今日のひとこと」。NULLまたは24文字以内の1行テキスト）
- remaining_chips
- total_rebuy_count
- outstanding_rebuy_count
- settlement_rebuy_count
- joined_at
- submitted_at
- created_at
- updated_at

同じ game_id と group_player_id の組み合わせは1件だけとする。

### game_rebuy_events

ゲーム中のリバイ操作履歴を表す。

- command_id（同じPOST再送を冪等化する一意UUID）
- game_participant_id
- event_type（rebuy、repayment、undo、adjustment）
- total_delta
- outstanding_delta
- recorded_by_type（participant、organizer）
- reverts_event_id
- recorded_at

通常のリバイ・返済、Undo、主催者修正は履歴を削除せず差分イベントとして残す。参加取消ではgame participantと一緒に削除する。今回のUIでは完全なタイムラインを表示しないが、将来の開催イベント表示に利用できる時刻を保存する。

### 参加時の選択肢

- 登録済み group_player から自分を選ぶ
- 新しい名前を入力し、players と group_players を作成して参加する

主催者による事前メンバー登録画面は補助機能として存在してよいが、参加に必須ではない。

新しい名前で参加したplayerは、そのグループのgroup_playersへ恒久登録する。次回以降は登録済みプレイヤーとして選択できる。

### プレイヤープロフィール

- 名前・一言・アイコン・マイハンドのプロフィール本体はplayersに1件だけ持ち、グループ固有の装備実績だけはgroup_playersに持つ
- ユーザーネームは1〜40文字、一言メッセージは任意で160文字以内とする
- アイコンは1枚までとし、画像本体は非公開R2、object keyとメタデータはplayersへ保存する
- 本人だけがユーザーネーム、一言、アイコンを編集できる
- マイハンドと、グループ内で獲得済みの実績からプロフィールに表示する1件を、既存プロフィール保存操作でまとめて編集できる
- 表示実績はグループ所属ごとに0件または1件とし、未獲得実績や他プレイヤーの獲得実績は選択できない
- 新しい名前で参加した端末は、そのplayerの本人端末として同時に登録する
- 事前登録済みplayerは主催者発行の本人用リンクで初回登録する
- 本人用リンクは確認POST時に1回だけ消費し、単に開いただけでは消費しない
- 使用済み、期限切れ、主催者による再発行済みの本人用リンクは無効とする
- 本人端末Cookieを失った場合は、主催者が本人用リンクを再発行できる
- 名前・一言・アイコンは個人戦績など参加者向け画面で公開してよい
- スマートフォンではページ全体を横スクロールさせず、指標切替や選択肢は画面幅内で折り返して表示する
- 個人ページでは実績マスタ全体と獲得状況、獲得日、獲得契機の開催をコレクションとして表示し、プロフィール見出しには装備中の実績だけを小型バッジで表示する
- 称号コレクション内の獲得契機となった開催名は参照情報として表示するだけとし、開催詳細へのリンクにはしない
- ランキング一覧では各プレイヤー名の直下に装備中の実績だけをコンパクトな称号バッジで表示し、順位・損益・参加回数を圧迫しない
- ランキングは累計損益、平均損益、最大勝ちBB、最大負けBB、直近3参加の平均損益BB、TOP3回数、平均順位率を切り替えられ、カードには選択中の指標だけを表示する
- ランキング一覧は確定済み開催への参加が1回以上あるプレイヤーだけを表示し、参加0回のグループメンバーは表示しない
- 平均順位率は開催ごとの`順位 ÷ 参加人数 × 100`の平均とし、低いほど上位とする。最近の調子には上振れ・下振れ等の評価ラベルを付けない
- 個人詳細の戦績サマリーは参加回数、優勝回数、TOP3率、プラス収支率を主要指標とし、各率には該当回数と参加回数を併記する。プラス収支率は損益BBが0より大きい開催だけを数え、0BBは含めない
- hidden実績は未獲得時に名称と条件を公開せず、獲得後に通常表示する
- 実績は本人の確定済み参加履歴だけから判定し、参加・優勝・損益BBに加えて、リバイ後の結果、返済完了、連続ノーリバイ、前回からの順位変化、4位・2位の累計、連続優勝を条件とする。個別条件は`docs/domain-rules.md`を正本とする
- 1開催で複数実績を獲得できるが、同じ実績はグループ内プレイヤーごとに1件だけ保持する
- 確定結果の訂正後は正式な確定履歴全体から実績を再評価し、成立しなくなった実績を解除する。解除対象を装備中の場合は未装備へ戻す
- ハンバーガーメニューのログアウトは、プロフィール取得・更新や参加者向けレート制限に依存せず、本人端末Cookieの削除だけを行ってグループTOPへ戻る
- 本人のプロフィール編集の最下部（表示する称号の後）に開催通知のON/OFFを設け、通常のプロフィール表示では通知設定を常設しない。通知先はplayerごとに最新のPWAインストール1台だけ保持する
- 通知を別端末でONにした場合は以前の通知先を置き換え、その端末で新しい開催の通知を受け取る
- 結果確定後は、その開催の参加者かつ通知ONのplayerだけへ結果確定通知を送り、通知タップで開催結果を開く。受付開始・結果確定の本文末尾には`🃏`を表示し、感嘆符は使わない
- 通知許可は利用者がONを操作したときだけ要求し、自動で許可ダイアログを表示しない
- 通知設定には、iPhone・iPadではホーム画面に追加したRiverCheckからのみ通知を利用できる旨を常時表示する。ホーム画面に追加していない場合は、PWAから設定するよう案内する

### 共通エラー導線

- 400、403、404、409、429、500系の画面表示エラーはRiverCheck共通のエラー画面で案内する
- 共通エラー画面には日本語の説明と「トップへ戻る」導線を常に表示する
- ブラウザの通常遷移に対してWorkerまたはフレームワークが素のテキストエラーを返した場合も、HTTP statusを維持したまま共通エラー画面へ置き換える
- JSONや画像などのresource response、React Routerのデータ通信は共通画面への置き換え対象にしない

## 7. 参加者tokenと端末識別

- 参加時に暗号学的に安全なランダムtokenを発行する
- DBへはSHA-256ハッシュだけを保存する
- 平文tokenをサーバーログ、HTML、URL、DBへ残さない
- 平文tokenは参加したブラウザへ保持する
- 同じ開催内で、使用中の同一 group_player を別tokenから選択できない
- 使用中の場合は「この参加者はすでに使用中です」等を表示する
- 本人Cookieを利用できない場合は、主催者が参加取消を行い、本人が同じ名前で参加し直す
- 参加取消では、その開催の入力済みremaining_chips、リバイ状態、リバイイベントも削除する
- 主催者画面の参加取消はアプリのデザインに合わせた確認モーダルを経て、画面遷移なしで一覧から即時反映し、成功・失敗を数秒間のトーストで通知する

ブラウザ内の具体的な保存手段は、セキュリティとCloudflare Workers構成を踏まえて architecture.md で決める。

## 8. 参加者入力

- remaining_chips: 0以上のsafe integer
- total_rebuy_count: 0以上のsafe integer。移行前の確定結果はNULL可
- outstanding_rebuy_count: 0以上かつ累計以下のsafe integer
- settlement_rebuy_count: 終了時入力前はNULL、入力後は0以上のsafe integer
- status_text: open中だけ本人が変更できる任意の1行テキスト。24文字以内とし、空欄保存はNULLへ正規化する
- 数字入力を中心としたスマホファーストUIにする
- 保存後は入力済みの値を確認画面に表示し、「入力を修正する」から再編集できる
- finalized前は本人tokenで更新できる
- finalized後は結果入力を変更できない。TABLE STORIESの本人投稿だけは追加・修正・削除できる

## 9. 点数

```text
score = remaining_chips - settlement_rebuy_count × rebuy_chips
```

domain層の純粋関数として実装する。点数は負になり得る。順位判定とDB保存は整数の`score`を使用する。

確定結果、共有文、個人戦績では、初期チップを100BBとして`score`から初期スタックを差し引いた「損益BB」を表示する。

```text
chips_per_bb = initial_chips / 100
net_bb       = (score - initial_chips) / chips_per_bb
```

初期チップ20,000の場合、40,000点は+100BB、20,000点は0BB、10,000点は-50BBと表示する。正数には`+`、負数には`-`を付け、0は符号なしとする。損益BBは最大小数第2位まで表示し、不要な末尾の0は省略する。確定結果では損益BBの正数を緑、負数を赤、0をニュートラル色で表示し、1BBあたりのチップ量を併記する。
確定結果では1位をWINNER領域へ集約して順位リストへ重複表示せず、2位以下を順に並べる。各参加者は損益BBの直下に精算額を置き、最終スタックとリバイ・終了時未返済を同じ補助情報単位で省略せず表示する。

## 10. 順位

順位は次の順で決める。

1. score の降順
2. total_rebuy_count の昇順。移行前のNULLだけsettlement_rebuy_countを代用
3. 完全同点は group_player_id のUnicode辞書順

共同順位は作らない。3番目は結果を再現可能にするための決定的tie-breakであり、優劣を意味しない。詳細は docs/domain-rules.md を正とする。

## 11. チップ総量検算

当初プロンプト中の改行崩れは加算として解釈する。

```text
expected_total = initial_chips × participant_count
               + rebuy_chips × total_settlement_rebuy_count

reported_total = sum(remaining_chips)
difference     = expected_total - reported_total
```

- difference = 0 は一致
- 正数は報告チップ不足
- 負数は報告チップ過多
- 差分があっても警告後に主催者判断でfinalize可能
- 未入力者がいる間は残チップ0・終了時リバイ証0枚として暫定検算を表示し、未入力者名と暫定値であることを明記する。全員入力まではfinalize不可とする
- 確定可能なチップ差分は黄色の警告として表示し、確定不能なエラーの赤と区別する

## 12. 会費の順位別傾斜精算

### 精算総額

```text
settlement_total = ceil(venue_cost / 100) × 100
```

- 標準・ゆる傾斜のおすすめ配分は従来どおり上位3位を起点に全順位を生成する
- シンプル割り勘は100円単位に切り上げた均等額を下位から配り、切り上げ超過分だけ上位を安くする
- 手動調整後は各順位の入力額をそのまま使用し、他順位へ自動再配分しない
- 各負担額は0以上の100円単位とする
- 1位 <= 2位 <= ... <= 最下位とし、同額を許可する
- 全員の cost_share 合計を settlement_total と必ず一致させる
- 上記条件を満たした全順位配分をgamesへ保存し、finalizeで使用する
- 移行前の全順位配分が未保存の開催は、1〜3位固定・3位額最低保証・残額傾斜・最下位丸め差額調整の従来計算を使う
- 参加人数4人未満は設定不可とする
- 詳細アルゴリズムは docs/domain-rules.md を正とする

## 13. finalize

finalizeは1つのPostgreSQLトランザクションで実行する。

1. gameがfinalizedでないことを確認する
2. game_participantsを取得・必要に応じてロックする
3. scoreを計算する
4. rankingを計算する
5. cost_shareを計算する
6. game_resultsへ確定値をINSERTする
7. game.statusをfinalizedへ変更する
8. finalized_atを更新する
9. 途中失敗時は全処理をrollbackする

game_participants は参加者入力の現在値、game_results は現在公開している確定結果とする。通常のルール変更で過去結果を再計算しないが、主催者が明示的に結果訂正した場合だけ両方を同一トランザクションで更新し、訂正前後をgame_result_revisionsへ保存する。

## 14. 結果表示と共有

確定後は順位、表示名、損益BB、会費負担額を表示し、一覧の末尾に全員の会費負担額の合計と1BBあたりのチップ量を表示する。

### 会費の回収確認

- 確定済み開催の結果画面には、主催者認証中だけ「会費の回収」を表示する。参加者画面、短縮公開リンク、ランキング、プロフィールには表示しない
- 独立した管理画面は設けず、確定結果の下に現在の受取済み人数と対象人数、未回収人数をまとめた折りたたみUIを置く
- 会費負担額が1円以上の参加者を回収対象とし、主催者が参加者ごとに「未回収」と「受取済み」を切り替える。0円の参加者は対象外として表示する
- 受取状態の切り替えはタップ直後に画面へ反映し、参加者ごとに独立して保存する。1人の保存中も他の参加者を連続して操作でき、保存失敗時は対象者だけ直前状態へ戻してエラーを表示する
- 受取済みへ変更した日時を保存し、全対象者が受取済みなら回収完了と表示する
- この状態はPayPayその他の決済サービスによる入金確認ではなく、主催者が実際の受取を確認するための内部記録とする
- 確定結果の訂正で会費負担額が変わった参加者は受取確認を解除する。金額が変わらない参加者の確認状態は維持する

### 確定後の結果訂正

- 開催は`finalized`のまま維持し、受付中へ戻さない
- 主催者画面の確定結果下部から訂正モードを開く
- 訂正できるのは既存参加者の`remaining_chips`、`total_rebuy_count`、`settlement_rebuy_count`だけとする
- 参加者の追加・削除、開催条件・会費設定の変更は訂正対象にしない
- 確定済みの会そのものを削除するUIは設けない
- 保存前に訂正後の順位、損益BB、会費負担額、チップ差分をプレビューする
- チップ差分がある場合は、通常確定と同様に主催者の明示確認を必須とする
- 訂正時はゲーム・参加者・現在結果をロックし、訂正前後のスナップショット保存、参加者入力更新、順位・会費再計算、現在結果置換を1つのPostgreSQLトランザクションで行う
- 既存の共有URLと短縮URLは変えず、保存完了までは参加者へ訂正前結果を表示する
- 保存後は管理者・参加者の両画面に「訂正済み」、訂正番号、訂正日時を表示する
- 訂正履歴には入力変更だけでなく、それに伴って変わった全参加者の順位、損益BB、会費負担額を訂正前→訂正後で表示する

確定済みの主催者画面は、確定結果と共有欄、TABLE STORIESの表示、結果訂正だけを表示する。参加者用リンク、参加状況、精算設定、チップ検算は確定後には重複表示しない。主催者本人の投稿も本人の参加者投稿として編集する。

共有操作は主催者画面だけに表示し、参加者用URLでは確定結果の閲覧だけを提供する。共有文の見出しには開催名を使用し、BBの計算式や換算説明は含めない。対応端末ではWeb Share APIでLINE、SNS、メール等の共有先を選択でき、結果文と短縮公開リンクを分離せず1つのテキストとして共有する。未対応環境では同じテキストをコピーする。短縮公開リンクはgame UUIDの推測耐性を維持した22文字のURL安全なコードを使用し、確定済み開催だけを既存の参加者用URLへ転送する。既存URLも引き続き利用でき、参加者tokenがないブラウザでもfinalized後は共有URLから確定結果を参照できる。

```text
【8月8日 ポーカー会】
合計：11,400円（8人）

🥇1位：A +238.5BB 0円
🥈2位：B +96.5BB 500円
🥉3位：C +42BB 1,000円
4位：D +15BB 1,500円
...

結果を見る
https://example.com/r/AAAAAAAAAAAAAAAAAAAAAA
```

### TABLE STORIES

- 開催詳細では、主催者を含む全員の投稿を1つの「TABLE STORIES」として同じカードUIで表示する
- 投稿者は必ず実在する参加者へ紐づけ、固定の「主催者」名義や主催者専用投稿を作らない。主催者本人も自分のプレイヤー名、アイコン、開催結果を伴う通常投稿として扱う
- TABLE STORIESは開催結果画面の精算より下に配置する。未投稿の参加者にはヘッダーに新規追加用の＋アイコンを表示して入力モーダルを開き、投稿済みの場合は本人カードだけに別意匠の編集アイコンを表示する
- 参加者は確定後に任意の本文1件と写真1枚を保存できる。本文だけ、写真だけを許可し、両方なしで保存した場合は投稿を削除する
- 参加者本文は最大160文字のプレーンテキストとし、Markdownは扱わない
- 1開催につき各参加者1投稿とし、finalized後に開催結果の同じモーダルから本人が追加・修正・削除できる。本人カードだけに編集アイコンを表示し、保存後も同じ開催詳細に留まる
- TABLE STORIESはfinalized後だけ表示・投稿でき、保存した投稿は即時公開する
- 主催者はfinalized後のTABLE STORIESから任意の参加者投稿を確認ダイアログ付きで削除できる。削除後は即座に非表示とし、削除日時と削除主体の監査情報だけをDBへ残す
- 開催詳細の参加者投稿はモバイルで縦1列、デスクトップで2列とし、横スクロールにはしない
- 写真はJPEG・PNG・WebPを受け付け、ブラウザで長辺1,800px以内のWebPへ縮小・圧縮する。サーバーでもcontent type、ファイルシグネチャ、圧縮後3MB上限を検証する
- R2 bucketは非公開とし、open中は本人または主催者だけ、finalized後は開催詳細の閲覧者へ、現在DBで参照中のobjectだけを専用routeから配信する
- PostgreSQLには画像本体ではなく、R2 object key、content type、byte size、uploaded_atを保存する。参加者投稿のobject keyは `groups/{groupId}/games/{gameId}/stories/{uuid}.{ext}` とする
- 画像更新ではR2とPostgreSQLの分散トランザクションを作らない。DB保存に失敗した新画像、置換・削除後の旧画像はbest effortで削除し、削除失敗時もDB参照を復元しない
- TABLE STORIESの各投稿にはリアクションを付けられる。第一弾は Fluent Emoji Flat の5種類（爆笑・熱い・えぐい・ナイス・GG/リスペクト）で固定し、表示素材はアプリ内に同梱する
- 同じプレイヤーは1投稿へ複数種類のリアクションを付けられるが、同一種類は1回までとする。再度押すと解除でき、自分の投稿にも付けられる
- リアクションはその開催への参加有無を問わず、同じグループでプロフィール認証済みのプレイヤーが付けられる。ゲスト閲覧者は件数だけを参照でき、リアクション操作はできない
- 投稿カードには付いている種類だけをアイコンと件数で表示し、プロフィール認証済みプレイヤーには追加ボタンから5種類の選択肢を表示する。自分が付けている種類は選択状態を明示する
- リアクション操作はOptimistic UIで即時反映し、保存失敗時だけ直前状態へ戻す。同じ種類の保存中は重複送信を抑止するが、別種類は並行して操作できる
- 将来の年間集計で「リアクションした量」を評価する場合、押したスタンプ総数ではなく `COUNT(DISTINCT story_post_id)` 相当の「リアクションした投稿数」を主指標とし、1投稿へ複数種類を付けても1投稿として数える

## 15. データモデル

最低限次を持つ。

- groups: グループ、公開コード
- players: 人そのもの
- group_players: グループ所属
- games: 開催設定、状態
- game_participants: 受付中の参加状態、当日ひとこと、入力値
- game_story_posts: 参加者ごとの任意投稿、写真のR2メタデータ、主催者削除監査
- game_table_events / game_table_event_players: 72o・BOMB POT・ALL INのテーブルイベント、関係者・勝者、記録主体、取消監査
- game_results: 確定結果のスナップショット
- game_result_revisions: 訂正番号、訂正日時、訂正前後の確定結果スナップショット
- game_cost_share_receipts: 確定済み開催で主催者が確認した参加者ごとの会費受取日時
- achievements: 実績名、説明、アイコンkey、カテゴリ、公開方法、表示順を持つ実績マスタ
- player_achievements: グループ内プレイヤーが獲得した実績、獲得日時、獲得契機の開催

`group_players.equipped_achievement_id`は、そのグループ内プロフィールに表示する実績を0件または1件保持する。`player_achievements(group_player_id, achievement_id)`の一意制約で二重獲得を防ぐ。

UUID、外部キー、一意制約、金額・チップの整数制約を使用する。現在の詳細スキーマは migrations 配下を参照する。

- 結果確定通知も、その開催の参加者かつ該当グループで通知ONのplayerだけへ送る

- Web Pushの個別失敗は開催作成や結果確定を失敗させず、無効になった通知先はPushサービスの404または410応答時に削除する
- 「このアプリについて」では現在提供中の参加、リバイ・返済、終了時入力、結果・PayPay精算、ランキング、プロフィール、称号を案内する
- 「このアプリについて」では、01〜05の使い方案内の後に、開催通知・当日連絡用LINEオープンチャットへの外部リンクを独立した導線として表示する
- iPhoneのホーム画面追加手順は補助情報として初期状態を閉じ、利用者が必要な場合だけ展開できるようにする
- Service Workerは公開静的アセットだけをキャッシュし、HTML、`.data`、認証・参加・結果・精算・プロフィールのresponse、POSTを保存しない
- オフライン中の参加や結果入力は提供せず、最新データを取得できないことを案内する
- 新versionは自動検出し、未保存入力の消失を避けるため利用者の明示操作後に切り替える
- 通常の画面・機能追加ではService Workerの手動ファイル一覧更新を不要とする

## GAME TIMELINE（確定後の振り返り）

finalized の開催結果画面では、リバイ・100BB返済とゲーム中に任意記録したテーブルイベントを、`recorded_at` の古い順に1本の `GAME TIMELINE` として表示する。見出しは「今日の卓の記録」とする。

リバイ・返済は精算・検算に関係する正式記録として `game_rebuy_events` を正本のまま維持し、テーブルイベントは精算へ一切影響しない振り返り用の `game_table_events` として分離する。`undo` は取り消し対象の元リバイイベントごとタイムラインから除外し、救済修正用の `adjustment` も表示しない。取消済みテーブルイベントも表示しない。表示対象が0件の場合はセクション自体を表示しない。

第一弾のテーブルイベントは次の3種類とする。

- 72o成立: 開催の72oルールがONの場合だけ記録でき、達成した参加者1人を選択する
- BOMB POT: 開催のBOMB POTルールがONの場合だけ、追加入力なしで記録する
- ALL IN: 参加者を2人以上選択し、その中から勝者を1人以上選択する。スプリットを考慮して複数勝者を許可する

テーブルイベントはopen開催の参加者または主催者が記録できる。選択対象はその時点で開催へ参加中のプレイヤーだけとし、サーバー側でも開催状態・参加者・ローカルルール設定を再検証する。テーブルイベントは編集せず、誤記録は取消して再登録する。通常参加者は自分が登録したテーブルイベントだけ、主催者は全テーブルイベントを取り消せる。取消は物理削除せず取消日時と取消主体を保持する。

開催中の参加者画面には「テーブルイベント」入口を表示し、72o、BOMB POT、ALL INを少ないタップ数で登録できる。最近のテーブルイベントを同じUI内に最大5件表示して取消導線を提供する。ポット額、スタック、ホールカード、ボード、ベット履歴、自由コメントは入力しない。

確定後の表示ではリバイ・返済をコンパクトな運営記録、72o・BOMB POT・ALL INを視覚的に強いハイライトとして同じ縦ライン上へ配置する。ALL INの敗者に対するリバイが記録時刻の前後3分以内に存在する場合は、DB上の関連付けを作らず表示上だけALL INの続きとしてまとめる。テーブルイベントの有無や記録失敗は結果入力、検算、finalize、精算をブロックしない。

TABLE STORIESは確定後に参加者本人が残す投稿、今日のひとことはopen開催中の現在状態、GAME TIMELINEは卓で起きた出来事として役割を分離する。今日のひとこと変更はGAME TIMELINEへ流さない。

## 結果確定の取り消し

主催者は、誤操作で確定した開催に限り、参加者・リバイ履歴・終了時入力を保持したまま確定結果を削除して受付中へ戻せる。取り消し時は対象開催の`game_results`を削除し、`games.status`を`open`、`finalized_at`をNULLへ戻したうえで、対象参加者の実績を残存する確定開催から再計算する。確定時に保存した会費設定は保持する。

結果訂正履歴、会費受取記録、TABLE STORIESのいずれかが確定後に存在する開催は、安全のため確定を取り消せない。送信済みPush通知は取り消さず、再確定時は通常どおり結果確定通知を送る。
