- 会話だけに存在する仕様を残さない
- docs/architecture.md は技術設計、docs/domain-rules.md は業務計算の詳細を補足する

## 1. 目的

Google スプレッドシートで行っているポーカー会の結果入力、順位計算、チップ総量検算、会費精算を、スマートフォンから使いやすい Web アプリへ置き換える。

最初の MVP は、1つのグループで実際のポーカー会を最初から最後まで運用できる状態を目標とする。

将来は次へ拡張する。

- 複数グループ
- 過去開催履歴
- 個人戦績
- ランキング
- 個人ダッシュボード
- グループダッシュボード
- 他ユーザーによるグループ作成・利用

将来拡張を妨げないデータ設計とするが、MVPで不要な機能や抽象化は先行実装しない。

## 2. 利用者

### 主催者

- 開催を作成する
- 開催を参加受付可能な状態にする
- 参加者用リンクを共有する
- 参加状況と入力状況を確認する
- チップ総量の差分を確認する
- 結果を確定する

### 参加者

- 主催者から共有された参加者用リンクを開く
- 登録済みプレイヤーから自分を選ぶ、または新しい名前で参加する
- 自分の残チップとリバイ回数を入力・修正する
- 確定後の結果と精算額を確認する

MVPではログイン機能やユーザーアカウントを設けない。

## 3. 正式な利用フロー

### 3.1 主催者が開催を作る

1. グループTOPから新規開催画面を開く
2. 開催条件と想定参加人数を入力する
3. 想定参加人数に応じた順位別の会費負担額を確認しながら条件を調整する
4. games に open 状態で保存する
5. 開催の主催者画面へ移動する
6. 参加者用リンクを LINE 等で共有する
7. finalized にするまでは、参加人数の変動に応じて開催条件と金額を変更できる

### 3.2 参加者が自分で参加する

1. 参加者は共有された開催URLを開く
2. 登録済みプレイヤー一覧の自分の行にある「参加」を押す、または新しい名前を入力して「この名前で参加」を押す
3. サーバーはランダムな participant token を発行する
4. participant token の平文は参加者のブラウザだけに保持する
5. DBには participant token のハッシュだけを保存する
6. 同じ開催・同じ group_player が既に別tokenで使用中なら参加を拒否する
7. 同じブラウザに正しいtokenが残っている場合は、その参加者として再開できる
8. open 中は途中参加を受け付ける
9. ドタキャン時は主催者が参加者を開催から外せる

「招待」とは、主催者が参加者を事前にチェック選択することではなく、参加者用リンクを共有して各参加者が自分で参加することを指す。

登録済みプレイヤー一覧は、確定済み開催への参加回数が多い順、同数なら最終参加開催日が新しい順、その後は表示名順とする。常連を自動的に上へ表示し、MVPでは手動のお気に入り・並び順管理を設けない。

### 3.3 参加者が結果を入力する

1. 参加者は自分の remaining_chips と rebuy_count を入力する
2. 主催者が finalize するまでは同じブラウザから修正できる
3. finalized 後は編集できない

### 3.4 主催者が結果を確定する

1. 参加者の入力状況を確認する
2. expected_total、reported_total、difference を確認する
3. difference が0でない場合は警告を表示する
4. 警告を確認したうえで、差分があっても主催者判断で finalize できる
5. finalize処理で点数、順位、会費負担を計算する
6. 確定値を game_results に保存する
7. gameを finalized にする

## 4. URL

### 参加者用

```text
/g/:groupCode/games/:gameId
```

このURLは参加、本人確認、結果入力、確定後結果表示の入口とする。主催者画面では「共有リンク」として表示し、入力欄右側のコピーアイコンからクリップボードへコピーできる。

### 主催者用

MVPの主催者ホームはグループ単位の専用URLとする。

```text
/g/:groupCode/manage
```

各開催の管理画面は次のURLとする。

```text
/g/:groupCode/games/:gameId/admin
```

主催者画面は開催の作成、開始、条件変更、参加状況確認、参加取り消し、検算、finalizeを担当する。

同じ端末で参加済みの場合、主催者画面に現在の参加者名を表示し、その人の入力画面へ戻る導線を設ける。主催者画面と参加者画面の往復ではフルページ読込を行い、開催ごとの本人Cookieを必ず再判定する。

参加者向けグループTOPと各参加者画面には、迷子防止のため主催者画面への導線を表示する。主催者画面、会作成、メンバー管理、開催管理の全loader/actionは主催者認証を必須とし、未認証時はPIN・合言葉入力画面へ移動する。

認証成功時はPIN自体ではなく有効期限付きの署名済みセッションをHttpOnly、SameSite=LaxのCookieへ180日保存し、本番HTTPSではSecureも付与する。Cookie改ざん、期限切れ、Cloudflare Secret未設定の場合は管理操作を許可しない。PINとCookie署名鍵はCloudflare Secretで管理し、Git、HTML、URL、DBへ保存しない。

## 5. 開催

開催作成時に次を設定する。

- title
- played_at（日付のみ。新規作成時は今日）
- initial_chips（1以上。画面表記は「初期チップ（100BB）」、新規作成時は20,000）
- venue_cost
- first_place_cost
- second_place_cost
- third_place_cost

`rebuy_chips` は利用者が個別設定せず、常に `initial_chips` と同じ値を保存する。新規作成時の会費は11,330円、1〜3位の負担額はそれぞれ0円、500円、1,000円を初期値とする。これらは初期値にすぎず、少人数時に1位を0円以外にする場合を含め、open中は自由に調整できる。

games.status は最低限次を持つ。

- open: 参加受付・入力可能。条件変更と参加者増減が可能
- finalized: 結果確定済み。参加者による入力と開催条件の編集は不可。主催者による確定結果訂正だけを許可

開催作成時点で open とし、基本状態遷移は open → finalized とする。逆方向へ戻さない。

### 開催条件の変更

- 管理画面では基本情報とチップ設定を再編集せず、会費の精算設定だけを表示する
- open の間は、会費、人数、1〜3位負担額を変更できる
- 精算の丸め単位は100円固定で、画面には入力欄を設けない
- finalized 後は変更できない
- open 中に条件を変更しても、参加者の入力済み remaining_chips と rebuy_count は保持する
- finalize 時点の最新設定を点数・検算・精算へ使用する
- 会費精算の人数と実際の参加人数が一致しない場合はfinalizeできず、確定ボタン付近に理由を表示する
- 精算設定の独立した保存操作は設けず、finalize成功時に精算設定と確定結果を同一トランザクションで保存する
- finalize失敗時は精算設定も保存せず、入力値とエラーを画面に残す
- finalize失敗時のエラーは確定ボタンの直前に表示する

### 順位別負担額プレビュー

新規開催作成画面と開催条件編集画面に、想定参加人数を入力するプレビューを設ける。

- 想定参加人数を変更すると、1位から最下位までの負担額を即時表示する
- 全順位を順位ごとの金額パネルで確認できる
- settlement_total と全順位の cost_share 合計も表示する
- 合計が一致することを画面上で確認できる
- 成立しない設定は保存前に理由を表示する
- プレビューは保存対象の参加者ではなく、金額確認用の仮人数とする
- 新規作成時に設定した想定人数を開催条件として保存し、参加人数の増減では自動変更しない
- open 中は想定人数を手動変更して別人数の金額も試算できる
- プレビューと finalize は同じ domain の calculateCostShares を使用する
- 「標準傾斜」と「ゆる傾斜」のボタンから1〜3位のおすすめ額を即時反映でき、反映後も手入力で修正できる
- おすすめ反映時は `max(想定人数, 現在の参加人数, 4)` で計算し、現在の参加人数が想定を超えていれば想定人数も更新する

## 6. プレイヤーと参加者

### players

人そのものを表す。display_name を持ち、同名を許可する。識別にはUUIDを使う。

### group_players

プレイヤーのグループ所属を表す。同じ player が将来複数の group に所属できる。

### game_participants

開催中の参加状態と現在入力値を表す。

- game_id
- group_player_id
- participant_token_hash
- status
- remaining_chips
- rebuy_count
- joined_at
- submitted_at
- created_at
- updated_at

同じ game_id と group_player_id の組み合わせは1件だけとする。

### 参加時の選択肢

- 登録済み group_player から自分を選ぶ
- 新しい名前を入力し、players と group_players を作成して参加する

主催者による事前メンバー登録画面は補助機能として存在してよいが、参加に必須ではない。

新しい名前で参加したplayerは、そのグループのgroup_playersへ恒久登録する。次回以降は登録済みプレイヤーとして選択できる。

## 7. 参加者tokenと端末識別

- 参加時に暗号学的に安全なランダムtokenを発行する
- DBへはSHA-256ハッシュだけを保存する
- 平文tokenをサーバーログ、HTML、URL、DBへ残さない
- 平文tokenは参加したブラウザへ保持する
- 同じ開催内で、使用中の同一 group_player を別tokenから選択できない
- 使用中の場合は「この参加者はすでに使用中です」等を表示する
- 本人Cookieを利用できない場合は、主催者が参加取消を行い、本人が同じ名前で参加し直す
- 参加取消では、その開催の入力済みremaining_chipsとrebuy_countも削除する
- 主催者画面の参加取消はアプリのデザインに合わせた確認モーダルを経て、画面遷移なしで一覧から即時反映し、成功・失敗を数秒間のトーストで通知する

ブラウザ内の具体的な保存手段は、セキュリティとCloudflare Workers構成を踏まえて architecture.md で決める。

## 8. 参加者入力

- remaining_chips: 0以上のsafe integer
- rebuy_count: 0以上のsafe integer
- 数字入力を中心としたスマホファーストUIにする
- 保存後は入力済みの値を確認画面に表示し、「入力を修正する」から再編集できる
- finalized前は本人tokenで更新できる
- finalized後は参照のみ

## 9. 点数

```text
score = remaining_chips - rebuy_count × rebuy_chips
```

domain層の純粋関数として実装する。点数は負になり得る。順位判定とDB保存は整数の`score`を使用する。

確定結果と共有文では、初期チップを100BBとして`score`を正規化した「BBスコア」を表示する。初期100BBは差し引かない。

```text
chips_per_bb = initial_chips / 100
bb_score     = score / chips_per_bb
```

初期チップ20,000の場合、20,000点は+100BB、-180,000点は-900BBと表示する。正数には`+`、負数には`-`を付け、0は符号なしとする。BBスコアは最大小数第2位まで表示し、不要な末尾の0は省略する。確定結果では正数を緑、負数を赤、0をニュートラル色で表示し、1BBあたりのチップ量を併記する。

将来の個人戦績では、`net_bb = bb_score - 100`により累計損益BBと平均損益BBを算出できる。確定結果のBBスコアと個人戦績の損益BBを混同しない。

## 10. 順位

順位は次の順で決める。

1. score の降順
2. rebuy_count の昇順
3. 完全同点は group_player_id のUnicode辞書順

共同順位は作らない。3番目は結果を再現可能にするための決定的tie-breakであり、優劣を意味しない。詳細は docs/domain-rules.md を正とする。

## 11. チップ総量検算

当初プロンプト中の改行崩れは加算として解釈する。

```text
expected_total = initial_chips × participant_count
               + rebuy_chips × total_rebuy_count

reported_total = sum(remaining_chips)
difference     = expected_total - reported_total
```

- difference = 0 は一致
- 正数は報告チップ不足
- 負数は報告チップ過多
- 差分があっても警告後に主催者判断でfinalize可能
- 未入力者がいる間は残チップ0・リバイ0回として暫定検算を表示し、未入力者名と暫定値であることを明記する。全員入力まではfinalize不可とする
- 確定可能なチップ差分は黄色の警告として表示し、確定不能なエラーの赤と区別する

## 12. 会費の順位別傾斜精算

### 精算総額

```text
settlement_total = ceil(venue_cost / 100) × 100
```

- 1〜3位は入力された固定額を使う
- 固定額は100円単位とし、1位 <= 2位 <= 3位とする
- 4位以下は3位の負担額を最低額として保証する
- 保証額を除いた残額を順位が下がるほど負担が減らないように配分する
- 各負担額は100円単位とする
- 丸め差額は最下位で調整する
- 全員の cost_share 合計を settlement_total と必ず一致させる
- 参加人数4人未満は設定不可とする
- 詳細アルゴリズムは docs/domain-rules.md を正とする

## 13. finalize

finalizeは1つのPostgreSQLトランザクションで実行する。

1. gameがfinalizedでないことを確認する
2. game_participantsを取得・必要に応じてロックする
3. scoreを計算する
4. rankingを計算する
5. cost_shareを計算する
6. game_resultsへ確定値をINSERTする
7. game.statusをfinalizedへ変更する
8. finalized_atを更新する
9. 途中失敗時は全処理をrollbackする

game_participants は参加者入力の現在値、game_results は現在公開している確定結果とする。通常のルール変更で過去結果を再計算しないが、主催者が明示的に結果訂正した場合だけ両方を同一トランザクションで更新し、訂正前後をgame_result_revisionsへ保存する。

## 14. 結果表示と共有

確定後は順位、表示名、BBスコア、会費負担額を表示し、一覧の末尾に全員の会費負担額の合計と1BBあたりのチップ量を表示する。

### 確定後の結果訂正

- 開催は`finalized`のまま維持し、受付中へ戻さない
- 主催者画面の確定結果下部から訂正モードを開く
- 訂正できるのは既存参加者の`remaining_chips`と`rebuy_count`だけとする
- 参加者の追加・削除、開催条件・会費設定の変更は訂正対象にしない
- 会そのものを削除するUIは設けない
- 保存前に訂正後の順位、BBスコア、会費負担額、チップ差分をプレビューする
- チップ差分がある場合は、通常確定と同様に主催者の明示確認を必須とする
- 訂正時はゲーム・参加者・現在結果をロックし、訂正前後のスナップショット保存、参加者入力更新、順位・会費再計算、現在結果置換を1つのPostgreSQLトランザクションで行う
- 共有URLは変えず、保存完了までは参加者へ訂正前結果を表示する
- 保存後は管理者・参加者の両画面に「訂正済み」、訂正番号、訂正日時を表示する
- 訂正履歴には入力変更だけでなく、それに伴って変わった全参加者の順位、BBスコア、会費負担額を訂正前→訂正後で表示する


確定済みの主催者画面は、確定結果と共有欄のみを表示する。参加者用リンク、参加状況、精算設定、チップ検算は確定後には重複表示しない。

共有操作は主催者画面だけに表示し、参加者用URLでは確定結果の閲覧だけを提供する。共有文の見出しには開催名を使用する。対応端末ではWeb Share APIでLINE、SNS、メール等の共有先を選択でき、結果文と公開リンクを分離せず1つのテキストとして共有する。未対応環境では同じテキストをコピーする。参加者tokenがないブラウザでも、finalized後は共有URLから確定結果を参照できる。

```text
【8月8日 ポーカー会】
合計：11,400円（8人）

🥇1位：A +338.5BB 0円
🥈2位：B +196.5BB 500円
🥉3位：C +142BB 1,000円
4位：D +115BB 1,500円
...

※BBスコア＝（残チップ－リバイ数×初期チップ）÷1BB
1BB＝200チップ（初期20,000チップ＝100BB）
```

## 15. データモデル

最低限次を持つ。

- groups: グループ、公開コード
- players: 人そのもの
- group_players: グループ所属
- games: 開催設定と状態
- game_participants: 開催中の参加状態と入力値
- game_results: 確定結果のスナップショット
- game_result_revisions: 訂正番号、訂正日時、訂正前後の確定結果スナップショット

UUID、外部キー、一意制約、金額・チップの整数制約を使用する。現在の詳細スキーマは migrations 配下を参照する。

## 16. 技術要件

- TypeScript
- React
- React Router v8 Framework Mode
- Cloudflare Workers
- PostgreSQL
- node-postgres（pg）
- Vitest
- Recharts（個人戦績のレスポンシブグラフ）
- loader/actionを使用し、MVPでは別REST APIを作らない
- route → service → repository → PostgreSQL の責務分離を維持する
- 業務計算はdomain層の純粋関数へ分離する
- SQLをrouteやReactコンポーネントへ書かない
- TanStack Query、Zustandは導入しない
- TanStack Tableは必要性が明確になるまで導入しない
- 秘密情報をソースコードへ直接記載しない

## 17. テスト方針

開発速度を優先し、MVP段階では高いcoverage目標、UIテスト、E2Eテスト、repositoryの網羅テストを必須にしない。

次のdomain関数はVitest unit testを必須とする。

- calculateScore
- calculateRanking
- validateChipTotal
- calculateCostShares
- calculatePlayerStats / addCumulativeNetBb

精算では100円固定、1〜3位の順位順、3位額の最低保証、4位以下の傾斜、合計一致、4人未満の拒否、丸め差額を確認する。

## 18. MVP対象外

- ユーザーアカウントとログイン
- 複数グループ管理UI
- 過去開催履歴
- 個人・グループダッシュボード
- 他ユーザーによるグループ作成
- 高度な監査、権限管理、レート制限

## 20. 仕様差異の修正状態

### 修正済み

- /games/:gameId/setup の主催者チェック選択を撤去した
