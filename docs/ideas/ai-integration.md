# AI応答API連携

- ステータス: アイデア・用途検討中
- 最終更新: 2026-08-09
- 対象: 開催振り返り、戦績、共有文、年間ハイライト、主催者支援
- API候補: Google Gemini等

## アイデア概要

Gemini等のAI応答APIとRiverCheckを連携し、確定済み結果やハイライトを材料に、手作業では作りにくい楽しい文章・紹介・振り返りを生成する。

AIは順位、損益BB、会費、回収状況等の正となる計算には使わない。既存の決定論的なService・domainロジックで確定したデータを入力として受け取り、その意味を壊さない範囲で文章生成・要約・演出を担当する。

## 目的

- 開催結果を単なる数字ではなく、読み物として楽しく振り返れるようにする
- 年末ハイライトやプレイヤー紹介文を少ない手間で作る
- LINE共有文、リマインド文等を場面に合うトーンへ整える
- RiverCheckに蓄積された戦績・称号・いいね・写真を横断して活用する
- 主催者の文章作成負担を減らす

## 活用候補

### 1. 開催振り返り文

確定済み結果をもとに、その回の短い振り返りを生成する。

例:

```text
第3回桜木町はPKサンダーが大勝！
終盤まで接戦だった上位陣を抜け、堂々の+238.5BBでした。
```

入力候補:

- 開催名・開催日
- 順位
- 損益BB
- ハイライト文
- 装備中の称号
- いいね数

事実としてDBにない試合展開・ハンド内容をAIに創作させない。

### 2. 年間ハイライト

`docs/ideas/game-likes-and-yearly-highlights.md` と連携し、年別集計から表彰コメントや年間まとめを生成する。

候補:

- 今年の最多優勝者紹介
- 今年一番いいねを受け取った人の紹介
- 今年一番みんなを称えた人の紹介
- 最大勝ちBB、最大復調、安定成績等の紹介
- 各開催の短いまとめ
- 「RiverCheck 2026 Awards」の総評

集計・受賞者選定はSQL・Serviceで確定し、AIは紹介文だけを書く。

### 3. LINE・共有文の生成

同じ結果データからトーンの異なる共有文を作る。

- 短く事務的
- 身内向けに少しネタ寄り
- 年末表彰風
- 初参加者にも分かりやすい説明付き

送信前に必ず主催者が内容を確認・編集できるようにし、自動送信はしない。

### 4. 精算リマインド文の調整

`docs/ideas/settlement-collection-management.md` と連携し、未回収金額等の確定値を変えずに、柔らかい催促文へ整える。

- 丁寧
- カジュアル
- 短文

金額、名前、開催名はAI出力から再抽出せず、テンプレート側で確定値を差し込む案を優先する。

### 5. ランキングの紹介

ランキングページで、数値から短い「プレイスタイル風紹介」を生成する。

例:

- 「波は大きいが、一撃の破壊力が魅力」
- 「安定して表彰台へ顔を出す常連」
- 「参加するたびに順位を上げている成長株」

人格・能力を断定せず、RiverCheck内の確定済み成績に基づく軽い娯楽表現に限定する。

### 6. 写真のキャプション候補

開催写真をAIの画像入力へ渡し、ハイライト用キャプション候補を生成する案。

写真には人物・会場等の個人情報が含まれるため、明示的な同意、外部送信先、保存方針を確認するまでは実装しない。

### 7. 称号の紹介文

`docs/ideas/player-achievements.md` と連携し、取得した称号に短い祝福文を付ける。

称号取得条件・取得判定はAIに任せず、既存ロジックで確定した称号だけを入力する。

## 初期実装として相性がよい案

最初は、主催者が確定済み開催画面から明示的に押したときだけ文章を作る「開催振り返り文生成」が安全で小さい。

```text
[AIで振り返り文を作る]
  → 生成中
  → textareaへ候補を表示
  → 主催者が編集
  → ハイライト文として保存、または共有文へ利用
```

利点:

- AIがなくても既存機能は動く
- 呼び出し回数と費用を制御しやすい
- 主催者が公開前に確認できる
- 現在のハイライトtextarea・共有機能へ自然に接続できる
- AI専用の大きな画面を先に作る必要がない

## AIへ任せないもの

- 順位計算
- チップ総量検算
- 損益BB計算
- 会費負担額計算
- 精算回収状態
- 称号取得判定
- いいね件数・年間受賞者の集計
- 本人認証・主催者認証
- 結果訂正の正当性判定

これらは既存のDB・Repository・Service・domainロジックを正とする。

## アーキテクチャ案

既存構成に合わせ、特定AIベンダーをrouteやReactコンポーネントから直接呼ばない。

```text
主催者用route action
  → AiContentService
  → AiTextProvider interface
  → GeminiAiTextProvider（初期候補）
  → Gemini API
```

用途別にServiceへ入力DTOを渡し、Providerはモデル固有のリクエスト・レスポンス変換だけを担当する。

将来別モデルへ切り替える可能性は考慮するが、複数AIを同時対応する過剰な抽象化は避ける。

## Cloudflare・Secret案

- APIキーをブラウザへ渡さない
- Cloudflare WorkerからAI APIを呼ぶ
- APIキーはCloudflare Secretへ保存する
- 例: `GEMINI_API_KEY`
- モデル名、タイムアウト、1日上限等は環境変数またはサーバー設定で管理する案を検討する
- ローカル開発では`.dev.vars`を使い、Gitへコミットしない

実装時点のGemini公式API仕様、利用可能モデル、料金、無料枠、データ利用条件を公式ドキュメントで再確認する。

## 費用・濫用対策

- 初期機能は主催者認証必須にする
- 自動生成ではなくボタン押下時だけ呼ぶ
- 1開催あたりの生成回数に上限を設ける
- 同じ入力の再生成を減らすため、生成結果を保存または短時間キャッシュする案を検討する
- 入力・出力文字数を制限する
- APIタイムアウトを設ける
- 失敗時は既存テンプレート文へフォールバックする
- 生成失敗で結果確定や精算が失敗しないよう、AI処理を本体処理から分離する
- Rate Limitingを適用する

## セキュリティ

- ハイライト文、一言メッセージ、開催名等のユーザー入力を命令として扱わず、AIへのデータとして区切る
- プロンプトインジェクションを前提に、AIへSecretや内部情報を渡さない
- AI出力をHTMLとして直接描画しない
- 初期実装はプレーンテキストのみとする
- 出力文字数、禁止用途、公開前確認を設ける
- APIキーや生レスポンスをクライアント・ログへ出さない
- エラーログへ参加者名や精算金額を過剰に残さない

## プライバシー

AIへ送信するデータは用途に必要な最小限にする。

- 可能ならプレイヤーIDではなく表示名と集計値だけを送る
- 精算回収状況・PIN・Cookie・tokenは送らない
- 写真は文章生成とは別権限・別確認にする
- AI利用中であることを主催者へ表示する
- 生成前に外部AIへ送る項目を説明する案を検討する
- ベンダー側の保存・学習利用・保持期間は実装時の規約を確認する

## 出力の正確性

AIが順位、名前、BBを誤記する可能性がある。

対策案:

- AIには自由文部分だけを生成させる
- 名前、順位、BB、金額はアプリ側テンプレートで差し込む
- 構造化出力が必要な場合はschema検証する
- AI出力をそのまま自動保存・自動公開しない
- 主催者が編集・承認してから保存する
- DBにない試合展開やハンドを創作しないようプロンプトで制約する

## データ保存案

最初は既存のハイライト文へ主催者が採用した文章だけを保存し、AIの全生成履歴は保存しない案を優先する。

将来必要になった場合の候補:

- `ai_generations`
- `group_id`
- `game_id`: nullable
- `purpose`
- `provider`
- `model`
- `prompt_version`
- `input_hash`
- `output_text`
- `created_by`
- `created_at`

個人情報・費用・監査の観点から、生成履歴を保存する目的と保持期間を決めずに先行実装しない。

## 実装前に確認する項目

1. 最初の用途を開催振り返り文にするか
2. Geminiを初期Providerとして採用するか
3. AI利用を主催者だけに限定するか、将来参加者にも開放するか
4. AIへ送るデータ項目
5. 1開催あたり・1日あたりの生成上限
6. 生成文をハイライトへ直接入れるか、共有文専用にするか
7. 採用した生成文だけ保存するか、生成履歴も保存するか
8. 写真入力は別タスクとして保留するか
9. 年間ハイライト機能と同時実装するか、AI基盤だけ先に作るか

## 段階的な実装案

### 第1段階: 開催振り返り文

- 主催者限定
- 確定済み結果を入力
- Gemini等で短い候補文を生成
- textareaへ表示
- 主催者が編集して保存
- API失敗時も既存画面を継続利用可能

### 第2段階: 共有・リマインド

- LINE共有文のトーン変更
- 精算リマインド文の候補生成
- 用途別プロンプト管理

### 第3段階: 年間・個人ハイライト

- 年間表彰コメント
- ランキング紹介
- 称号取得時の祝福文

### 第4段階: 画像入力

- 写真キャプション
- 明示的な同意・プライバシー対応
- 画像送信上限と費用管理

## 完了条件案（第1段階）

- 主催者が確定済み開催から明示的に生成できる
- 順位・BB等の計算をAIへ任せていない
- APIキーがクライアント・Git・ログへ漏れない
- 生成回数・入力・出力に上限がある
- AI失敗で結果・精算・ハイライト編集が壊れない
- 生成文を主催者が確認・編集してから保存できる
- DBにない出来事を事実として断定しない
- プレーンテキストとして安全に表示される
- Provider・Service・routeの責務が分離されている
- 必要なunit testと外部APIモックテストがある
