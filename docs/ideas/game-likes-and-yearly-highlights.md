# 開催いいね・年間ハイライト

- ステータス: アイデア・要件確認待ち
- 最終更新: 2026-08-09
- 対象: 過去開催結果、プレイヤー交流、称号、年間振り返り

## アイデア概要

確定済みの過去開催画面から、その回で良かったプレイヤーへ赤いハートの「いいね」を送れるようにする。

開催ごと・プレイヤーごとのいいね数を永続保存し、単にその場で褒めるだけでなく、将来の年間ハイライトや称号取得の入力データとして使う。

## 目的

- 勝敗や損益BB以外の観点でも参加者を称えられるようにする
- 過去開催画面を、結果を見るだけではなく後から反応できる場所にする
- 「たくさん称えた人」「たくさん称えられた人」の両方を可視化する
- 年末に、その年のコミュニティを振り返る楽しい紹介ページを作れるデータを蓄積する
- いいね数を永久取得型の称号条件へ利用する

低評価・バッドボタンは作らず、ポジティブな反応だけを扱う。

## 現時点で残す要件

- いいねは赤いハートで表現する
- 確定済みの過去開催画面から押せる
- 各結果のプレイヤー行にハートボタンと合計数を表示する
- 主催者専用ではなく、参加者側から押せる
- いいね数をDBで永続管理する
- 開催別・受け取った人別・押した人別に集計可能にする
- 将来の年間ハイライト・ランキングの入力データとして使えるようにする
- 「累計N回いいねをもらった」等を称号条件に利用可能にする

## 画面案

### 過去開催結果

各プレイヤーの結果行へ、次のような小さな反応欄を置く。

```text
PKサンダー   1位   +238.5BB     ♡ 4
```

- 未押下はアウトラインのハート
- 自分が押した後は赤く塗られたハート
- 押した瞬間に軽い拡大アニメーションを入れる
- 数字はその開催でその人が受け取った合計
- スマホで順位・BB・会費を圧迫しない位置へ置く
- 連打で増殖せず、同じ人から同じ相手へのいいねは最大1件とする案を優先する
- もう一度押すと取り消せるトグル方式を候補とする

### 年間ハイライト（将来）

例: `/g/:groupCode/highlights/:year`

勝敗ランキングとは別に、その年のコミュニティ活動を紹介するページとする。

候補:

- 「今年一番愛された人」: 受け取ったいいね最多
- 「今年一番みんなを称えた人」: 送ったいいね最多
- 「ハートを配る人」: いいねした開催数が最多
- 「満場一致」: 1開催で多くの参加者からいいねを受け取った
- 「ナイスゲーム」: いいね総数が最も多かった開催
- 月別・開催別の印象的ないいね

ランキングだけでなく、カード形式の短い紹介文を並べる「年末の表彰ページ」にする案を優先する。

## 称号機能との連携候補

称号は `docs/ideas/player-achievements.md` の思想に合わせ、一度取得したら永久保持する。

### 受け取った人

| 称号候補 | 条件案 |
| --- | --- |
| はじめての♥ | 累計1いいねを受け取る |
| 愛され上手 | 累計10いいねを受け取る |
| ハート泥棒 | 累計30いいねを受け取る |
| 満場一致 | 1開催で、その回の他参加者全員からいいねを受け取る |

### 押した人

| 称号候補 | 条件案 |
| --- | --- |
| ナイスの民 | 累計10いいねを送る |
| ハート配り | 累計30いいねを送る |
| 褒め上手 | 5開催以上で誰かへいいねを送る |

称号条件の正確な件数は、実際の利用頻度を見て実装前に調整する。

## 誰が押したかの識別

「たくさん押した人」を集計するには、いいねした本人をプレイヤーへ紐付ける必要がある。

既存の本人端末Cookieで認証できているプレイヤーを、いいね送信者として使う案を優先する。

- ログイン中のプレイヤーは、その本人としていいねできる
- いいね送信時に `from_group_player_id` を保存する
- 公開画面では誰が押したかの個人名一覧は出さず、合計数だけ表示する案を優先する
- 年間ページでは送信数・受信数の集計結果を表示可能にする

「誰でも押せる」を未認証端末まで含める場合、匿名いいねは送信者ランキングへ含められない。端末Cookieだけで匿名IDを作る案もあるが、Cookie削除で重複可能になるため、実装前に方針確認が必要。

## データ設計案

### game_player_likes（仮称）

- `id`
- `group_id`
- `game_id`
- `from_group_player_id`
- `to_group_player_id`
- `created_at`
- `updated_at`
- `UNIQUE(game_id, from_group_player_id, to_group_player_id)`

制約案:

- 対象gameは`finalized`のみ
- 送信者・受信者は同じgroupに所属する
- 受信者はその開催の確定結果に存在する
- 自分自身へいいねできるかは実装前に決める
- 取り消しを許可する場合はDELETE、履歴を残す場合は`revoked_at`方式を検討する

集計しやすいよう、いいね数をプレイヤーテーブルへ直接加算せず、イベント行を正としてCOUNTする。

## API・処理案

既存アーキテクチャに合わせる。

```text
過去開催action
  → 本人端末認証を確認
  → LikeServiceで開催・送信者・対象者を検証
  → LikeRepositoryで追加または取り消し
  → 対象行の最新件数を返す
```

- React Routerのactionを利用する
- ページ全体を再読み込みせず、押した行だけ即時更新する
- 二重送信はUNIQUE制約で防ぐ
- CSRF、連打、Rate Limitingを既存方針に合わせて検討する
- いいね追加・取り消しの競合でも件数が壊れないよう、保存行を正とする

## 年間集計の基準案

年間ハイライトで年を判定する候補は2つある。

- 開催日 `games.played_at` の年を使う
- いいねを押した `created_at` の年を使う

その開催への評価という性質から、開催日の年で集計する案を優先する。年をまたいで後から押されたいいねを前年へ加えるか、締切を作るかは未決定。

## プライバシー・雰囲気

- いいねはポジティブな称賛用途に限定する
- 誰から誰へ押したかを通常画面へ公開するかは慎重に決める
- 初期実装では受信合計のみ公開し、送信者の個別一覧は本人・主催者にも不要とする案を優先する
- 年間ページでは集計されたランキング・表彰だけを表示する
- いいねが少ない人を目立たせるワースト表示は作らない
- 0件ランキングや最下位表示は避ける

## 実装前に確認する項目

1. 「誰でも」は本人端末認証済みプレイヤー全員という意味でよいか、未認証の閲覧者も含むか
2. 自分自身へいいねできるか
3. 1開催で複数人へ1回ずついいねできるか
4. いいねを後から取り消せるか
5. 誰が押したかを他の参加者へ公開するか、合計数だけにするか
6. いいね可能期間を無期限にするか、開催後N日等の締切を設けるか
7. 年間集計は開催日の年を基準にしてよいか
8. 初期実装に称号連携まで含めるか、データ蓄積だけ先行するか
9. 年間ハイライトページは別タスクとして後から実装するか

## 段階的な実装案

### 第1段階: いいね収集

- 確定結果の赤いハートボタン
- 本人認証
- 1送信者・1対象者・1開催につき最大1件
- 合計数表示
- 押下・取り消しの即時反映

### 第2段階: 個人集計・称号

- 送った数・受け取った数の集計
- プロフィールまたはランキングへの表示
- 永久取得型称号への連携

### 第3段階: 年間ハイライト

- 年別集計
- 年末の表彰カード
- 最多受信・最多送信・最多いいね開催等の紹介

## 完了条件案（第1段階）

- 確定済み開催の結果行から赤いハートを押せる
- 同じ送信者が同じ相手へ連打して件数を増やせない
- ハート状態と合計数が画面更新後も保持される
- 複数端末からの同時操作でも件数が壊れない
- 開催途中や存在しない結果へいいねできない
- 未認証時の動作が合意した仕様どおりになる
- スマホで順位・BB・会費表示を圧迫しない
- 将来の送信数・受信数・年別集計に利用できるデータが残る
- Repository・Service・純粋な集計ロジックへ必要なunit testがある
